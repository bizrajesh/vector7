# Decisions

Where the build prompt left a choice open, the simplest safe option was taken and recorded here.

## Platform and hosting

1. **Laravel 13 / PHP 8.3+**, Blade, Tailwind 3 pre-built into `public/css/app.css` (committed). The server never runs Node.js.
2. **One cron entry** (`schedule:run` every minute). The scheduler runs `queue:work --stop-when-empty --max-time=50` each minute for queued email, plus the daily/hourly jobs in `routes/console.php`. No Supervisor, Redis or long-running workers.
3. **Cache, sessions and queue use the database** (works on Hostinger shared hosting).
4. **Hostinger document root:** Option A symlinks `public_html` → `vector7/public`. Option B (project inside `public_html`) uses `deploy/hostinger/root.htaccess`, which rewrites into `public/` and denies private folders.
5. **`composer.lock` is not committed** in this branch: the lock produced in the build environment pointed at local package mirrors. Run `composer install` once (it resolves from Packagist and writes a lock) and commit that lock if you want fixed versions.
6. **HTTPS** is forced by `public/.htaccess` on any host except `localhost`, `127.0.0.1` and `*.test` (so Laragon keeps working), and by `FORCE_HTTPS=true` for generated links. HSTS is sent on HTTPS requests.

## Authentication and permissions

7. **Two guards**: `web` (staff: App and tenant users, `/workspace/login`) and `customer` (`/login`). Customers are separate records owned by the App workspace.
8. **No OTP or two-factor login in this release.** The "Two-factor authentication" setting exists in App Settings → Security, defaults to Off and is disabled ("coming later"). Sensitive actions (refund decisions, settings changes) ask for the current password again.
9. **Lockout**: 5 wrong passwords lock the account for 15 minutes; counters are per account, and rate limits are applied per IP as well.
10. **Generated passwords** are 12 characters from an alphabet without look-alike characters (0/O, 1/l/I). They are shown once and only stored as a hash. Generation logs the actor and target (never the password) and logs the target out of other sessions.
11. **Permission matrix** lives in `config/permissions.php` (module × view/create/update/delete/export/approve). It is enforced by the `perm:` middleware on every workspace route; tenant isolation is a global `TenantScope` plus write guards on the `BelongsToTenant` trait, so a guessed ID from another tenant returns 404.
12. **App Manager** gets every App module except IAM, Settings and the audit log (the audit log is treated as part of IAM).
13. **Tenant custom roles** combine existing permissions only, within tenant modules.
14. **Support role** (tenant) can create, read and update tenant users (no delete) and can generate passwords for tenant users except Tenant Admins.
15. **Tenant file access**: any active user of a tenant can open that tenant's files through the permission-checked `/files/{id}` route (stored outside `public`, random file names); customers only get files attached to their own registration, payments or tickets.

## Business rules

16. **Working days** exclude Saturday, Sunday and the tenant's holidays; "within N working days" means the Nth working day after the start date.
17. **One active booking or sale per plot** is guaranteed by `SELECT … FOR UPDATE` on the plot row plus a unique `active_plot_lock` column on `bookings` and `sales`.
18. **Prices** are frozen on the booking (actual, offer, price used, promo discount, net), so later price or offer changes never affect it. A promo code applies on top of the price used.
19. **Payments are allocated** to instalments in order. A sale moves to ROR only when the balance due is zero.
20. **Refund** = paid − penalty, where the penalty row is chosen by days late after the sale window; it needs Tenant Admin approval, is recorded as an expense and releases the plot.
21. **Broker commission** is booked as an expense at sale initiation (category "Broker commission").
22. **Sold plots** leave the marketplace; their public URL redirects (301) to the project page.
23. **Enquiry → booking conversion** is recorded by entering the booking number on the enquiry (status "Converted"). A "Book plot" shortcut opens the booking form pre-filled with the enquired plot.
24. **Tenant help desk** covers tickets raised with the vector7 team. Buyers' questions to a promoter come in as enquiries.

## Masters and template

25. App-level masters (`tenant_id = NULL`) are seeded from `database/seeders/data/Vector7_Tenant_PreConfig_Template.xlsx` on install. A tenant copies them during setup ("use App defaults") or imports its own template; the import is all-or-nothing in one transaction.
26. Template roles map Admin → Tenant Admin, Manager → Tenant Manager, Sales → Tenant Sales, Accountant → Tenant Account.

## AI, marketing and integrations

27. **Claude** model defaults to `claude-sonnet-5-5` (editable in Settings). Every call is logged in `ai_usage_logs` and counts against the tenant's monthly AI credits, or against the App's monthly cap for App-level calls. Without an API key, features fall back to built-in templates or manual entry.
28. **Social publishing** uses the Meta Graph API for Facebook and Instagram (Instagram needs a launched project with a layout image). YouTube only publishes videos, so YouTube posts are prepared as title and description text to paste into YouTube Studio; channel metrics come from the YouTube Data API. Posts for platforms that are not connected stay drafts marked "Not connected".
29. **Payment gateway** (Razorpay or Swipe) is used only for tenant subscriptions, through the gateway's hosted payment-link page and a signature-verified webhook. Customer payments are recorded offline.
30. **Storage drivers** (Local, Google Drive, S3, GCS, Azure Blob) talk to each provider's REST API directly, with no SDKs, so nothing extra is needed on shared hosting.

## Demo data

31. `DemoSeeder` runs when `SEED_DEMO=true`. It drives the real services (estimate, Go decision, start, plot import, booking, sale, payments, registration), with dates spread over the last six months so dashboards and charts show history. It sends no emails. Demo logins use `Demo@2026`.

## Feature Update 01 (spec 17)

32. **Build order.** Leads (17.6) was built before Quick Launch (17.1), because every contact flow in 17.1–17.5 writes a lead. Parts 17.1–17.6 and the shared data model (17.11/17.12) went in as one commit; later parts are committed one by one.
33. **Enquiries become leads.** On upgrade, a migration copies every tenant enquiry into `leads` (stage mapped from the old status) and keeps the `enquiries` table. App-level enquiries (from the Support page) stay in `enquiries`. When the App team assigns one to a promoter, it is copied into that promoter's Leads. `/workspace/enquiries` permanently redirects to `/workspace/leads`.
34. **Duplicate leads merge** within a tenant by mobile number (last 10 digits) or email (case-insensitive). A closed (Won/Lost) lead that comes back is reopened as New. Different tenants never share leads.
35. **Images** are stored as StorageFile ids in `listing_images` (a 1600 px WebP and a 400 px thumbnail), not as paths, so every storage driver works. The old `projects.gallery` JSON was moved into `listing_images`, and old gallery URLs redirect (301) to the new image URLs.
36. **Quick-launch plot errors** are checked before anything is saved, using an unsaved Project. On errors the form comes back with the row errors, and the photos and layout must be chosen again, because browsers cannot refill file inputs.
37. **Project contact relation** is called `contactBlock`, because `projects.contact` is an existing phone-number column. A layout with no contact block uses the promoter's default contact settings and the project's phone number.
38. **Contact gating.** Call, WhatsApp and Show number ask once per browser session for name, mobile and consent. After that the session remembers the visitor, and each later click still logs an activity on the same (merged) lead. Reveals are limited to 5 a minute and 30 a day per IP. Without JavaScript the form posts and the page comes back with the number.
39. **Search covers both** published listings and available plots in launched layouts. Plots are grouped into one "layout" card per project, showing the matching plot count and a "from" price. Searching for "plot" includes layouts. Layouts never appear in rent searches or BHK searches.
40. **Relaxation order** (when fewer than 5 results): widen the budget by 10% → add neighbouring districts from `config/districts.php` (editable) → drop free-text wishes one at a time, last first → ignore feature filters. The page lists every step that was applied.
41. **Claude never supplies results.** The AI only (a) turns the request into filters, using a strict tool schema, and (b) orders the top 30 database results with a one-line reason. Any key Claude returns that is not in the SQL results is discarded. Only key fields are sent, never contact details. Parse and rank results are cached for 1 hour. When AI is off, over its daily cap, or fails, a built-in English/Tamil keyword parser and SQL relevance order are used instead.
42. **Marketplace caches** (sitemap, category counts, known places) are cleared whenever a listing is saved or deleted. They are cached as arrays, because the database cache store does not unserialize objects.
43. **Sold or rented listings** answer **410 Gone** with similar properties, and drop out of search, the sitemap and category pages. Listings hidden by the App team, drafts and unpublished listings answer 404. Search pages with filters are `noindex,follow`. Clean category URLs (`/buy/flats/thanjavur`) are indexable and listed in the sitemap.
44. **Compare** works from a public `?keys=L:1,P:2` link (up to 3), so a shared link shows the same table. The shortlist and saved searches need a buyer account. Saved-search alerts email at most 5 new matches per run and never repeat an item (`saved_search_matches`).
45. **Chatbot leads need the visitor's own consent.** The marketplace bot's `create_lead` tool only proposes a lead. The lead is created when the visitor fills in their name and mobile and ticks consent in the chat window, through a separate endpoint that also checks the bot really proposed that property. The model never sees contact numbers.
46. **Workspace assistant scope.** It uses read-only tools, each tied to a permission (and to the plan module for Leads), and every tool runs inside the user's workspace. Claude is only offered the tools the user's role allows. Sales see their own and unassigned leads; Support sees no money data. The only write is "create follow-up", done by a separate endpoint after **Confirm**, which re-checks permission and lead visibility. "Apply" puts a draft into the text box the user last clicked; nothing is saved until they save the form.
47. **AI credits.** The workspace assistant charges the workspace's monthly AI credits. When they run out (or the plan has no AI), it still answers from the help pages and runs simple data shortcuts, and says why. The marketplace bot and AI search are charged to the App's daily caps per feature group.
48. **Conversations** are kept for 90 days for both bots (`v7:chat-purge` runs daily at 03:30). A workspace conversation continues for 12 hours, then starts fresh. Assistant tables can be downloaded as Excel by the user who asked.
49. **Tool names follow the spec.** Marketplace bot tools: `search_listings`, `get_listing`, `get_layout_plots`, `get_promoter_public_info`, `get_services`, `get_faq` and `create_lead`. Workspace tools: `count_plots`, `list_bookings`, `list_due_instalments`, `list_leads`, `lead_details`, `project_summary`, `expense_summary`, `usage_summary` and `list_listings`. App users get `app_tenants`, `app_subscriptions`, `app_usage` and `app_tickets`.
50. **Money totals.** Sales users have Accounts *view* (to issue receipts), but spec 17.13 says Sales must not get accounts totals. So `expense_summary` and `project_summary` require **Reports → view**, which Admin, Manager and Accounts have and Sales does not.
51. **Signed-in buyers** who have a mobile number on their account see the number straight away when they tap Call or Show number. The click is still recorded as a lead with their account details. Number reveals are also limited per customer (40 a day) as well as per IP.
52. **Listing cards** show Call / WhatsApp / Enquire buttons for the enabled modes. Each button opens the listing's contact block, so the masking, consent and lead rules always apply in one place.

## Feature Update 01 follow-up: languages, menus, App sign-in

53. **Language scope.** Tamil / English applies to the public marketplace and the buyer account pages, which are buyer-facing. The promoter workspace, the App workspace, staff sign-in pages and all emails are always English: `SetMarketLocale` forces `en` on `/workspace`, `/app`, `/files` and `/profile`, whatever the visitor chose. The choice comes from `?lang=`, then the session, then a 1-year cookie. Default is English.
54. **Translation keys are the English text** (`lang/ta.json`), so an untranslated string simply stays in English. User-entered content (listing titles, descriptions, project and promoter names) is not translated. Seeded App data (features, services, plan descriptions) is translated through the same file. Saved SEO texts are English, so Tamil pages use the translated default titles and descriptions. `hreflang` links point to the `?lang=` versions, and the canonical URL stays the same.
55. **Menu filters.** Buy, Rent and Layouts reuse one search page with a *context*. The context decides the type pills, budget presets (lakhs and crores vs monthly rent) and type-specific filters (furnishing, water source, space type, approving authority, corner plots). These were added to `PropertySearch` as optional filters. Rent with no type is limited to rentable types, and layouts never appear for rent.
56. **App sign-in is separate** (`/app/login`) and is not advertised anywhere public, including `robots.txt`. Both staff sign-in pages run the same lockout rules (`LoginService::attempt`) with a per-page check of who may sign in there.
57. **Tamil without AI.** The keyword parser maps common Tamil words and place names (`config/tamil_words.php`, with case-ending stems such as தஞ்சாவூரில்) to English before parsing, so Tamil searches work even when AI is off.
58. **Five plan items.** Plans are designed on storage, projects, plots, users (all roles) and active listings. *Plots* counts every plot across the tenant's layouts and is checked when plots are imported (new plot numbers only; re-imports don't count). *Users* counts every workspace user. The old per-role user limits were added up into the new total, and the per-role limits stay as optional caps (−1 = no cap), because many promoters only want one total.
59. **Professional → Growth.** The seeded plan is renamed in place (same row, so subscriptions stay). A plan the App team has already renamed is left alone.
60. **Free listings floor.** "5 free active listings" is an App setting (`listings.free`). A tenant's listing limit is never below it, and it still applies when the subscription has expired, while every other limit needs a running plan. Photo size is also an App setting (`listings.image_max_mb`, default 5 MB).
61. **Top-up term and price.** A bought top-up lasts until the current plan period ends, the recommended option when the person had no preference. Pack prices are per month, so a top-up costs *price × quantity × months left* (calendar months, rounded up, with a couple of days' slack). Top-ups need a running plan. The App team can grant free top-ups with any end date, or none.
62. **Top-ups are billed on subscription invoices** (`kind = topup`, `plan_id` nullable). They reuse the same payment links, webhook, manual *Mark paid* and PDF invoice as plan invoices, instead of a parallel billing table.
63. **Who pays for a contact view.** The person's answer was that the buyer pays a small amount to view a contact, the money goes to the App owner, and the free alternative is a call-back request with contact mode and preferred time that shows up in the tenant's enquiries. The fee is GST-inclusive, so buyers see one round number; the receipt splits out 18 % GST. It is per buyer and per property, valid for N days, and requires a signed-in customer account so the unlock follows the buyer across devices.
64. **No gateway, no charge.** Contact view charges only apply while Razorpay or Swipe is configured, because a buyer cannot be asked to pay offline for a phone number. Without a gateway, numbers stay free and the App screen warns about it.
65. **Paid views still create leads.** After paying, the buyer's Call, WhatsApp and Show number clicks are logged as leads for the promoter exactly as before. The promoter is not charged.
66. **Call-back requests.** These use the new lead source `callback` and store `preferred_mode` and `preferred_time` on the lead. They schedule a normal follow-up at the start of the chosen slot (morning 9:00, afternoon 12:00, evening 16:00, any time 10:00) on the chosen day, or on the next suitable day. That way the request shows up in the existing follow-up reminders and overdue counts. The tenant menu now says **Leads & enquiries**.
67. **Buyer FAQ wording.** The default chatbot FAQ and the Support page no longer say "free for buyers". They say browsing, call-back requests and booking are free and that seeing a number costs a small fee. An FAQ the App team has already saved in Settings is not overwritten.
68. **Razorpay return URL accepts GET.** The tenant invoice "verify" route now accepts GET as well as POST, because Razorpay returns to the callback URL with a GET. Before, the return page could fail even though the webhook still marked the invoice paid.
69. **Skip the project phase, two ways.** *Direct launch* (the existing quick launch) is now on Launch & plots and in the menu, so promoters can find it. *Skip to launch* lets a project already in the project phase move to Ready to Launch with its approval details, then use the normal launch screen (layout, plot onboarding, Go live). Stages and estimates are kept, not deleted, so the project can still be tracked later. It needs `launch.approve` and is audited.
70. **Property Listers are their own kind of tenant** (`tenants.type = lister`) with one *Property Lister* user. This reuses the listing, lead, contact, media, plan, top-up and help-desk code unchanged, so promoters' listing feature is untouched. Lister workspaces get none of the promoter roles or masters. The lister role is not one of the five roles a promoter can assign. Access is limited by the role's permissions (dashboard, listings, leads, help desk, own plan), and the menu and dashboard are lister-specific.
71. **Separate lister sign-in on the marketplace** (`/list-property`, `/list-property/login`), bilingual like the rest of the marketplace. Each sign-in page only accepts its own kind of account (buyer, promoter, lister, App). The lister workspace screens stay in English, like every workspace.
72. **Plans have an audience** (`promoter` | `lister`). Each audience has its own trial default, plan list on *My plan & usage*, upgrade path and public pricing tab. Listers can only buy listing and storage top-ups. Lister plans keep projects 0, plots 0, users 1, and their modules are fixed to Leads + AI.
73. **App Support** is a new App system role: help desk, enquiries, chatbot conversations and security monitoring, with read-only services, customers and listings moderation. It gets a work-queue home page instead of the business dashboard. "Handle service requests" means through the help desk: each service request already opens a ticket. The services catalogue and prices stay with App Admin and App Manager. App Manager does not get Security, matching how chatbot logs are restricted.
74. **Sign-in monitoring.** Every attempt through `LoginService` is recorded in `login_events`: portal, account, outcome (success / failed / locked / blocked), reason, IP, user agent, and the session ID on success. The password is never recorded, and recording can never block a sign-in. Signed-in sessions are read from the `sessions` table. Staff are matched by `user_id`; buyers by the session ID saved at sign-in, because the database session handler only stores the web guard's user. Ending a session deletes its row. Records are purged after 180 days.
75. **Preview gate instead of HTTP basic auth.** A Laravel middleware with its own sign-in page works the same on every Hostinger setup, including PHP-FPM and LiteSpeed, where `.htaccess` basic auth is unreliable. It shows the vector7 look, and attempts are logged in the Security screen. Only a bcrypt hash of the shared password is kept in `.env`, never in Git. The tester's browser keeps an encrypted cookie holding an HMAC of the email, the hash and APP_KEY, so changing the password signs everyone out. Webhooks and `/up` are exempt so payments and health checks still work.
76. **Closing sign-ups is a switch, not a code removal** (first `REGISTRATION_OPEN` in `.env`; replaced by decision 78). The three public sign-up routes for buyers, listers and promoters answer 403 with a friendly page. Staff-created accounts (App IAM, promoter IAM, walk-in buyers added by sales) are unaffected.
77. **Patta and survey numbers are private to the workspace.** They are removed from every public page, from the plot tooltip JSON (`Plot::tooltipData(internal: false)`) and from SEO / JSON-LD. Buyers see plot number, size, facing, boundaries and price.
78. **Sign-ups are an App Admin setting, one per account type** (`signup.buyer`, `signup.lister`, `signup.promoter` in App settings, default off). The App Admin can open them without server access. Routes use `signup:<kind>` middleware; every sign-up link checks `App\Support\Signups::open()`. `REGISTRATION_OPEN` in `.env` is gone.
79. **Three statuses on the marketplace.** `Plot::marketStatus()` maps available → Available, booked → Booked, everything else → Blocked. Tooltips, cards, map colours, legend, filters and the plot page use it; the workspace (`internal`) keeps the real status. Sold plots now stay on the public layout as Blocked (they used to disappear and their page redirected) so the layout map has no gaps.
80. **Plot onboarding uses the existing importer.** The new page only adds the template download, a project picker and the upload; the preview → fix → confirm flow and validation are the same as Launch & plots. Status by import stays Available / Blocked: Booked needs a real booking with a buyer, so it can't be imported.
81. **Test-data clean-up is a plain SQL file**, so it can be run from phpMyAdmin on Hostinger without SSH. It lists every table once; a test fails when a new table is added without being listed. Verified against a demo database: after the script the row counts equal a fresh install without demo data (apart from the kept App settings).
82. **Sold is shown to buyers too** (replaces part of 79): the marketplace shows Available, Booked, Sold or Blocked; only Sale Init, ROR-Init, ROR and ROR-Completed are folded into Blocked. Sold plots stay on the map and their page opens, marked Sold, with no Book button.
